동료 휴가로 자리를 비운 두 업무 모두를, Pick Release/RMA에 쓰던 Selenium·Playwright 기반 Salesforce 구동 기법으로 대신 처리한 2개 트랙의 백업 앱. Track A는 소모품 출고요청 메일 → ServiceMax Case/Parts Order 생성 → 오라클 Release, Track B는 엔지니어(FSE) 앞으로 오는 Shipping Only Parts Order를 찾아 Oracle Transfer Order로 직접 릴리즈한다. 둘 다 원래 대화형(Claude Code)으로 처리하던 흐름을 AI 호출 없이 배치 파일로 돌아가는 앱으로 다시 짜서, 비개발자인 팀원도 그대로 설치해 쓸 수 있게 만들었다. A two-track backup app covering both of a teammate's responsibilities while she was on leave, using the same Selenium/Playwright technique for driving Salesforce built for Pick Release and RMA. Track A: consumables request emails → ServiceMax Case/Parts Order creation → Oracle release. Track B: finds Shipping-Only Parts Orders addressed to field service engineers and releases them directly as Oracle Transfer Orders. Both replace what used to be a Claude Code conversation with an app that runs on batch files, zero AI calls at runtime, so any non-developer teammate could install and operate it.

왜 AI 없이 다시 짰나
Why rebuild without AI
Salesforce를 Playwright로 직접 구동하는 방식 자체는 본인이 Pick Release/RMA 자동화에서 이미 쓰던 기법이라 동료의 소모품 출고 업무에도 공유해뒀었다. 문제는 동료가 자리를 비운 동안 Claude Code 없이도 팀원이 이어받아 돌릴 수 있어야 한다는 점 — 그래서 대화형으로 처리하던 흐름을 규칙 기반 파서 + 고정 GUI로 재구성해, 토큰 비용도 없고 Claude Code 설치도 필요 없는 배치 파일 2개짜리 앱으로 다시 짰다. Send to Approval을 앱이 누르지 못하게 막은 것도 같은 이유 - 무인화 범위를 사람이 통제할 수 있는 만큼만 좁혔다.
Driving Salesforce directly via Playwright wasn't new — it's the same technique already used for Pick Release/RMA automation, shared into this parts-order workflow too. The problem was coverage: a teammate had to be able to run this without Claude Code while the usual owner was on leave. So the conversational, AI-assisted flow was rebuilt as a rule-based parser plus a fixed GUI — no token cost, no Claude Code install, just two batch files. Blocking the app from ever clicking Send to Approval follows the same logic: keep the unattended scope exactly as wide as a human can still supervise.

첫 실행에서 잡은 사고 - 당일 원인수정
A production incident caught on day one - root-caused same day
첫 실행(2026-09-01)에서 45건 중 5건이 중복 릴리즈요청 메일로 잘못 나갔다 - 이미 다른 플로우로 처리된 Billable 4건과 Order Status가 Closed인 1건인데, 자체 상태 파일만 믿고 발신함(Sent Items)을 대조하지 않은 게 원인. Closed 건은 관계형 리스트(Parts Order Lines)가 화면에 다 렌더링되기 전에 읽어 품목 0줄로 판단하고도 그대로 보낸 두 번째 버그가 겹쳤다. 발견 즉시 5건 모두 회수하고, 발송 전 Sent Items 대조(already_sent) + Order Status가 Open/Partial이 아니면 스킵 + 빈 라인이면 재시도 후에도 비면 스킵, 3개 가드를 그날 바로 추가했다. 이후 남은 40건은 20건 Billable 스킵 · 9건 Closed 스킵 · 12건 정상 릴리즈 · 4건 backorder 재시도로 정확히 갈렸다.
On the first run (2026-09-01), 5 of 45 candidates got a duplicate release-request email — 4 already-handled Billable orders and 1 Closed order — because the app trusted only its own state file instead of cross-checking Sent Items. The Closed case had a second bug layered on top: it read the Parts Order Lines related list before the page finished rendering, saw 0 lines, and sent anyway. All 5 were recalled immediately, and three guards went in the same day: an already-sent check against Sent Items before any send, a skip when Order Status isn't Open/Partial, and a retry-then-skip on empty line reads. The remaining 40 candidates then split cleanly: 20 skipped as Billable, 9 skipped as Closed, 12 released normally, 4 re-tried for backorder.
