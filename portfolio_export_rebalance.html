한국(KRP) 창고에서 해외 법인(호주·홍콩·중국·일본·미국·스페인)으로 재고를 옮기는 국가간 Transfer Order(Rebalance)를, 알림 감지부터 3PL 창고 조율, Oracle 트랜잭션, 통관 Commercial Invoice 발급, 수출신고실적 기입까지 전 구간을 잇는 14단계 SOP 풀사이클을 사람 명령 없이 이어서 실행하도록 코드화했다. 3PL(용마)이 위치정보를 회신하는 순간부터는 시스템이 알아서 끝까지 처리하고, 유일하게 시스템 밖에 남는 일은 물리적 행위(FedEx/DHL 실제 픽업 예약)뿐이다. Codes the full 14-step cycle of the cross-border Transfer Order (inventory rebalance) procedure — from the first system alert, through 3PL warehouse coordination, the Oracle transaction, the customs commercial invoice, to the export declaration — to run end to end with no manual command, for stock moving from the Korea (KRP) warehouse to sister companies in Australia, Hong Kong, China, Japan, the US, and Spain. The moment the 3PL (Yongma) replies with pick-location details, the system carries the case through to completion on its own; the only work left outside the system entirely is physically booking the FedEx/DHL pickup.

MAIL INSTEP 01
재배치 알림 감지
Rebalance alert detected
재고 이동 관리 리스트에 TO 번호가 배정되면 변경 알림 메일이 자동으로 날아온다. 본문에서 TO 번호와 출발·도착 법인, 파트를 읽어낸다. 한 TO에 파트가 여러 개면 파트마다 메일이 따로 오기 때문에 TO 번호 단위로 묶어 한 건으로 처리하고, 아직 TO 번호가 붙지 않은 등록 알림은 트리거 대상에서 제외한다.
When a TO number gets assigned on the stock-movement list, a change-notification email fires automatically. The body yields the TO number, the origin and destination entities, and the part. A single TO with several parts produces one email per part, so they're grouped by TO number into one case; notifications for entries that don't have a TO number yet are skipped as triggers.
SHAREPOINTSTEP 02
TO 상세 조회 — 파트/수량 확정
TO lookup — parts and quantities
알림에는 파트 하나만 담겨 있어서, 그 TO 번호로 목록을 다시 조회해 실제로 나가야 할 파트와 수량 전부를 확정한다. 수입 통관 자동화가 이미 쓰고 있던 목록 조회 방식을 그대로 재사용하고 조회 기준만 TO 번호로 바꿨다.
The alert carries only one part, so the list is queried again by TO number to establish every part and quantity that actually has to ship. It reuses the same list-lookup routine the import-side automation already relied on, just keyed on TO number instead.
MAIL OUTSTEP 03
3PL 창고에 제원·로케이션 요청
Asks the 3PL for dimensions and pick locations
파트와 수량을 채운 요청 메일이 창고 담당자 앞으로 바로 나간다. 여기서 사람이 하던 일은 "무엇을 몇 개 꺼내야 하는지 정리해서 메일 쓰기"였고, 그게 통째로 없어진 구간이다.
A request email, already populated with parts and quantities, goes straight to the warehouse contact. The human work here used to be compiling what to pull and how many, then writing the mail — that whole step is gone.
WAITING— · —
3PL 회신 대기 (매시간 스캔)
Waiting on the 3PL reply (hourly scan)
여기서만 시스템 밖의 시간이 흐른다. 회신이 언제 올지 모르니 매시간 폴더를 훑고, 도착하면 그 즉시 이어서 진행한다.
This is the only stretch where time passes outside the system. Since the reply can land at any hour, the folder is swept hourly and the case picks up the instant it arrives.
MAIL INSTEP 04
회신 파싱 + TO 매칭 판정
Parses the reply, judges the TO match
회신은 정해진 서식 없이 사람이 쓰는 대로 온다. 본문에서 TO 번호와 로케이터·수량을 뽑아내되, TO 번호가 확실히 특정될 때만 곧바로 다음 단계로 넘어가고 애매하면 자동 실행을 멈추고 사람 확인 알림만 보낸다 — 바로 다음이 실제 재고를 움직이는 구간이라 여기에 안전판을 뒀다.
Replies come in free-form, however the sender chose to write them. The TO number, locators, and quantities are extracted from the body — but the case only proceeds automatically when the TO number is unambiguous; anything murky halts and raises a human-review alert instead, because the very next stage moves real inventory.
ORACLESTEP 05–09
재고를 실제로 움직이는 5개 트랜잭션
The five transactions that actually move stock
회신이 파싱된 순간 사람 명령 없이 이어서 실행된다. 중간에 끊겨도 이미 통과한 단계를 다시 누르지 않도록 진행 상태를 단계별로 남기며 간다 — 재고 이동은 되돌릴 수 없어서 재시도와 중복 실행 방지를 같이 걸어야 했다.
Runs straight through with no manual command the moment the reply is parsed. Progress is recorded stage by stage so an interruption never re-clicks a step that already went through — inventory movement can't be undone, so retries and duplicate-execution guards had to be built together.

SHAREPOINTSTEP 10
Delivery 번호 역기입
Writes the delivery number back
Oracle에서 막 생긴 Delivery 번호를 재고 이동 목록에 되돌려 적는다. 해외 법인 쪽에서 이 값을 보고 입고를 준비하기 때문에, 여기가 비면 상대편이 물건을 기다리며 되묻는 메일이 오는 지점이다.
The delivery number Oracle just produced is written back onto the stock-movement list. The receiving entity works off that value to prepare inbound, so a blank here is exactly what triggers a "where is it?" email from the other side.
DOCUMENTSTEP 11–12
통관 Commercial Invoice 발급 + PDF 보정
Issues the customs invoice, then patches the PDF
수입 통관 자동화가 쓰던 인보이스 출력 경로를 그대로 재사용하되 출발지를 한국으로 돌려 발급한다. 오라클이 뽑아준 PDF에는 목적지 국가별 수하인 정보와 HTS 코드 칸이 비어 있어서, 서식을 새로 만들지 않고 원본 PDF의 빈 여백에만 값을 직접 얹는다 — 인쇄 레이아웃이 그대로 유지돼야 통관 서류로 쓸 수 있기 때문이다. 파트가 여러 개인 건은 행마다 HTS 코드를 각각 채운다.
Reuses the very same invoice-printing path as the import automation, just pointed outbound from Korea. Oracle's generated PDF leaves the destination-specific consignee block and the HTS code cells empty, so values are laid directly into blank space on the original rather than re-exporting a template — the print layout has to survive intact for the document to work at customs. On multi-part shipments, every line gets its own HTS code.
LEDGERSTEP 13
수출신고실적 기입
Files the export declaration record
인보이스에 이미 찍힌 값을 그대로 읽어 실적에 옮긴다. 다른 데서 다시 조회하면 인보이스와 어긋날 수 있어서, 발행된 인보이스를 단일 출처로 삼았다. 아래 컬럼 지도 참고.
Values already printed on the invoice are read straight off it and carried into the ledger. Looking them up elsewhere risks drifting from the issued document, so the invoice is treated as the single source. See the column map below.
DOCUMENTSTEP 14
최종 인보이스 보관
Archives the final invoice
수하인 정보까지 반영된 최종본을 정해진 파일명 규칙(출발지-목적지 + Delivery 번호)으로 보관 폴더에 저장한다.
The finished invoice, consignee details and all, is stored in the archive folder under the established naming rule — origin-destination plus delivery number.
MAIL OUTDONE
완료 회신 + 상태 기록
Completion reply and state record
처리 결과를 담당자에게 회신하고 상태 파일에 기록한다. 같은 TO가 다시 트리거돼도 두 번 처리되지 않는다. 이 시점에 남는 일은 택배사 픽업 예약 하나뿐이다.
The outcome is emailed back and logged to the state file, so the same TO can never be processed twice even if it triggers again. At this point the only thing left is booking the courier pickup.

13개 중 12개가 자동으로 채워진다. 남은 하나는 택배사가 픽업을 잡아야 번호가 생기는 트래킹 번호라, 시스템 안에서 미리 만들어낼 수 없는 값이다 — 이 프로젝트에서 사람이 하는 일이 정확히 거기 하나로 좁혀졌다. Twelve of the thirteen fill themselves. The remaining one is the tracking number, which doesn't exist until the courier books the pickup — nothing inside the system can conjure it. That single field is exactly what the human work on this project has narrowed down to.
