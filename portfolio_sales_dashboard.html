Sales Dashboard · 2025–2026

영업SALES
대시보드DASHBOARD

Firebase 기반의 실시간 영업 납품처 관리 시스템. 팀원별 분기 목표 추적, 다국어 지원, 대표 보고용 리포트까지 하나의 플랫폼에서 연결한 End-to-End 솔루션. Salesforce(CRM)는 실제 출하 확정(Ship Confirm) 여부와 무관하게 계약을 Closed Won으로 표시하기 때문에, CRM 상 계약 현황과 실제 매출 인식 시점 사이에 괴리가 생길 수 있다 — 이 대시보드는 Salesforce 데이터를 매주 자동 동기화하고, Ship Confirm을 매출 집계의 최종 게이트로 두어 그 괴리를 완화한다. 목표를 못 채울 것 같은 분기에는, 실제 데이터를 건드리지 않고 어떤 미확정 건을 추가로 확보하면 되는지 미리 계산해보는 가상 시나리오 모드도 함께 쓴다. A real-time Firebase sales-account management system. Per-member quarterly target tracking, multilingual UI, and an executive report — connected end-to-end in one platform. Salesforce (CRM) marks a deal Closed Won regardless of whether it has actually shipped, which can create a gap between what the CRM reports and when revenue is truly recognized. This dashboard closes that gap by auto-syncing Salesforce data every week and treating Ship Confirm as the sole gate for counting revenue. When a quarter looks short, a what-if scenario mode lets the team test which pending deals would close the gap — without ever touching the real numbers.

API가 없다
No API
이 리포트는 API로 뽑을 수 없어서, 사람이 하던 것과 똑같이 리포트 화면을 열고 기간 필터를 맞춘 뒤 Export 버튼을 누르게 했다. 로그인은 회사 SSO에 맡기고 전용 브라우저 프로필을 재사용해서, 계정 정보를 코드에 두지 않는다. The report cannot be pulled through an API, so the script opens the report screen, sets the date filter and clicks Export exactly as a person would. Login rides on the company SSO through a dedicated browser profile, so no credentials live in the code.
계약 단위로 본다
Grouped by deal
행 하나가 곧 계약이 아니라서, 계약 단위로 묶은 뒤 메인 제품 라인이 들어있는 건만 후보로 인정하고 금액은 그 계약에 딸린 라인 합계로 계산한다. 같은 계약에 함께 팔린 다른 시스템은 합계에서 빼고 별도 후보로 분리한다. A row is not a deal, so lines are grouped per opportunity; only groups containing a main product line become candidates, and the amount is the sum of that deal's lines. A separate system sold alongside it is pulled out of the total and split into its own candidate.
이미 쓴 건 건드리지 않는다
Never touches what is in use
후보가 이미 등록에 사용됐으면 덮어쓰지 않는다. 아직 안 쓴 후보만 최신 값으로 갱신하고, 이미 매출로 올라간 건은 금액만 고치고 담당자가 손으로 넣은 값은 그대로 둔다. Once a candidate has been used to register a deal it is never overwritten. Only unused candidates get refreshed, and for deals already counted as revenue only the amount is corrected, leaving every hand-entered field intact.
애매하면 자동으로 처리하지 않는다
Ambiguity stops the machine
분기가 바뀌었거나 같은 계약의 다른 건이 이미 등록돼 있으면 자동으로 반영하지 않고 표시만 남겨 사람이 판단하게 한다. 검토 없이 매출이 생기는 쪽이 훨씬 위험하다고 봤다. If the quarter shifted, or another line from the same deal is already registered, nothing is applied automatically; the case is flagged for a person to judge. Revenue appearing without review is the worse failure.

☁️
Salesforce 연동 · 수기 입력 간극 최소화
Salesforce Sync · Minimizing the Manual-Entry Gap
리포트에 API가 없어 Selenium이 리포트 화면을 열고 기간 필터를 맞춘 뒤 Export까지 눌러 파일을 받는다. 받은 파일을 계약 단위로 묶어 SO번호·계약구분·Acc Type(옵션킷 조합 자동계산)을 Firestore 후보 큐에 넣고, 영업팀이 담당자·제품·분기 필터로 검토한 뒤 클릭 한 번으로 등록한다. 같은 구조를 커미션 자동계산 등 다른 수기 업무로 확장할 수 있다.
The report has no API, so Selenium opens the report screen, sets the date filter and clicks Export to collect the file. What comes back is grouped per deal, and SO number, contract type and Acc Type (derived from the option-kit combination) land in a Firestore candidate queue, where the sales team filters by member, product or quarter and registers a candidate in one click. The same pipeline extends to other manual workflows, such as automated commission calculation.
07
🚢
Ship Confirm 게이트 · CRM-매출 괴리 완화
Ship Confirm Gate · CRM-Revenue Reconciliation
Salesforce는 실제 출하와 무관하게 계약을 Closed Won으로 표시한다. 이 대시보드는 상태를 Pending → Back up → ACT → Ship Confirm 4단계로 나누고, 매출 집계는 Ship Confirm 단계에서만 집계되도록 설계해 CRM 상 계약 현황과 실제 인식된 매출 사이의 괴리를 완화한다.
Salesforce marks a deal Closed Won independent of whether it has actually shipped. This dashboard splits status into four stages — Pending → Back up → ACT → Ship Confirm — and only counts revenue at the Ship Confirm stage, reconciling what the CRM reports against when revenue is actually recognized.
08
🧮
가상 시나리오 계산기 · 목표 역산
Scenario Simulator · Working Backward From Target
확정된 Ship Confirm 금액 위에 아직 미확정인 건들을 드래그로 얹어보며 "무엇을 더 확보하면 목표를 채우는지"를 계산한다. Firestore 원본에는 전혀 쓰지 않는 화면 전용 오버레이라 새로고침하면 완전히 원상복구되고, 실제 합계와 시나리오 합계를 나란히 표시해 확정치와 가정치가 섞이지 않게 했다.
On top of the amount already locked in at Ship Confirm, pending deals can be dragged in to test what would close the gap to target. It's a display-only overlay that never writes to Firestore, so a refresh restores the real numbers exactly — and the real and scenario totals are shown side by side so confirmed and hypothetical figures are never confused.
09
🔁
분기 전환 자동 이월
Automatic Quarter Rollover
새 분기가 시작되는 시점을 감지해, 직전 분기에서 Ship Confirm까지 가지 못한 건(ACT · Pending · Back up)을 현재 분기로 자동 이월한다. 이미 이월했는지는 별도 플래그로 기억해 중복 실행을 막는다.
Detects the moment a new quarter begins and automatically rolls forward any deal that never reached Ship Confirm in the prior quarter — ACT, Pending or Back up — into the current one. A flag remembers whether the rollover already ran, so it never fires twice.
10
🧾
감사 로그 · 커미션 이중차감 방지
Audit Log · Double-Commission Guard
매출 건 생성 · 수정 · 삭제, 담당자 변경, 분기 이동이 일어날 때마다 변경 전/후 값과 실행자를 별도 감사 로그 화면에 남긴다. 같은 계약이 여러 제품 라인으로 나뉘어도 외부 커미션은 대표 라인 하나에서만 차감해 이중 차감을 막는다.
Every create, edit, delete, owner change and quarter move is logged with a before/after snapshot and the actor's email on a separate audit page. When one deal spans multiple product lines, external commission is deducted from a single representative line only, preventing double counting.
