한국(KRP) 창고에서 나가는 수출 물량 세 갈래 — 해외 법인으로 재고를 옮기는 국가간 재배치(Rebalance), 미국 본사로 되돌려 보내는 반송(HQ RMA), 그리고 그 둘을 실제로 실어 보내는 FedEx 발송 어레인지 — 를 하나의 파이프라인으로 묶었다. 알림 감지부터 3PL 창고 조율, Oracle 트랜잭션, 통관 서류 발급, 수출신고실적 기입, FedEx 발송물 생성과 트래킹 번호 회수까지 이어진다. Three outbound tracks leaving the Korea (KRP) warehouse — cross-border inventory rebalance to sister companies, RMA returns to US headquarters, and the FedEx booking that physically carries both — wired into a single pipeline. It runs from the first system alert through 3PL warehouse coordination, the Oracle transaction, customs paperwork, the export declaration, and on to creating the FedEx shipment and collecting the tracking number.

수기 SOP를 그대로 옮겨 적은 것이 아니라, 코드로 옮기는 과정에서 SOP 자체를 다시 세웠다 — 창고에 보내는 요청 서식, 처리의 최소 단위, 실적의 출처, 되돌릴 수 없는 지점의 정의까지 7개 규칙을 재정립했다. The manual SOP wasn't merely transcribed into code — writing it down as code meant rewriting the procedure itself: seven rules were redefined, covering the request format sent to the warehouse, the unit of work, the source of truth for the ledger, and where the irreversible steps sit.

SOP Redefinition

SOP를 옮겨 적은 게 아니라The SOP wasn't transcribed
다시 세웠다— it was rewritten

수기 절차를 그대로 코드로 옮기면, 사람이 눈치로 메우던 빈칸이 그대로 자동화의 사고가 된다. 실제로 잘못된 수량이 벤더에게 나갔고, 배송이 갈린 건에서 서류 한 장이 조용히 빠졌다. 그때마다 코드만 고치지 않고 절차 자체를 다시 정의했다 — 아래 7개가 그 결과다. Transcribe a manual procedure verbatim into code and every gap a person used to paper over by instinct becomes an automated incident. A wrong quantity did go out to a vendor; on a split delivery a document did quietly go missing. Each time the fix was not only in the code but in the procedure itself — these seven are the result.

RULE 01
창고에 보내는 요청 서식을 고정한다Fix the request format sent to the warehouse
WAS평문으로 파트와 수량만 적어 보내고, 회신은 담당자가 쓰는 대로 자유서식으로 받았다.Parts and quantities went out as plain prose, and replies came back however the warehouse staffer chose to write them.
NOWItem / Qty / Locator / Serial 4컬럼 표를 붙여 보낸다. Item만 우리가 채우고 수량만큼 행을 미리 뽑아 여유 행까지 붙인다 — 나머지 칸은 창고가 채운다.A four-column table — item, quantity, locator, serial — goes with the request. Only the item column is pre-filled, with one row per unit plus spare rows; the warehouse fills the rest.
수량을 미리 채우려다 반려됐다. 시리얼이 붙는 제품은 개체마다 행을 쪼개야 하는데, 어느 파트에 시리얼이 있는지는 보내는 쪽이 알 수 없다. 아는 쪽이 채우게 두는 것이 정확하다.Pre-filling quantities was rejected: serialised items need one row per unit, and the sender has no way of knowing which parts carry serials. The side that knows should be the side that fills it in.
RULE 02
확인 안 된 정보는 보내지 않는다Never send what hasn't been confirmed
WAS목록 조회가 실패하면 수량 자리를 물음표로 둔 채 요청 메일이 그대로 나갔다.When the list lookup failed, the request email went out anyway with a question mark where the quantity belonged.
NOW품목·목적지·TO 번호·수량이 전부 확정되지 않으면 발송을 보류하고 처리 이력에도 남기지 않는다. 다음 회차가 같은 건을 자동으로 다시 시도한다.Unless item, destination, TO number, and quantity are all confirmed, the mail is held and the case is not marked processed — the next cycle retries it automatically.
부정확한 정보를 벤더에게 보내는 것은 정보가 없는 것보다 나쁘다. 잘못된 수량으로 창고가 준비를 시작하기 때문이다. 목록 검색이 몇 분씩 지연되는 특성도 실측으로 확인해, 단발 조회 실패를 "없음"으로 단정하지 않고 재시도로 흡수하게 바꿨다.Sending a vendor inaccurate data is worse than sending nothing — the warehouse starts preparing against the wrong quantity. The list search was also measured to lag by minutes, so a single failed lookup is no longer read as "not there" but absorbed by retries.
RULE 03
처리의 최소 단위는 TO가 아니라 배송이다The unit of work is the delivery, not the order
WAS한 TO를 한 건으로 처리했다. 오라클이 배송을 둘로 쪼개면 두 번째 인보이스가 서류에서도 실적에서도 조용히 빠졌다.One order was treated as one case. When Oracle split it into two deliveries, the second invoice vanished from both the paperwork and the ledger without a sound.
NOW인보이스·실적 행·본사 앞 서류 메일이 전부 배송 단위다. 본사 메일은 그 TO의 인보이스가 다 모이고 조용해질 때까지 큐에 모아 한 통으로 보낸다.Invoices, ledger rows, and the headquarters document mail are all per delivery. The headquarters mail waits in a queue until every invoice for that order has landed and gone quiet, then goes out as one.
실적 기입도 같은 이유로 바꿨다 — 목록에서 읽은 TO의 파트 전부가 아니라, 그 배송의 인보이스에 실제로 찍힌 파트만 기입한다.The ledger write follows the same logic: not every part on the order as read from the list, but only the parts actually printed on that delivery's invoice.
RULE 04
실적의 출처는 발행된 서류 하나뿐이다The ledger has exactly one source: the issued document
WAS실적 컬럼마다 편한 곳에서 값을 가져왔다. 자재명·단가·금액·원산지가 통째로 빈칸으로 들어간 적도 있다.Each ledger column pulled its value from wherever was convenient — item name, unit price, amount, and origin once went in entirely blank.
NOW금액·수량·원산지·품명은 발행된 인보이스 PDF에서 읽어 쓴다. 발송 어레인지도 같은 규칙을 따르고, 실적이 인보이스와 다르면 인보이스 값을 쓰되 불일치를 경고로 남긴다.Amounts, quantities, origin, and descriptions are read off the issued invoice PDF. The shipment booking follows the same rule: where the ledger disagrees with the invoice, the invoice wins and the mismatch is flagged.
서류와 실적이 어긋나면 나중에 어느 쪽이 맞는지 아무도 판정할 수 없다. 그래서 통관에 실제로 나간 서류를 기준으로 삼았다 — 반송 건의 신고가를 10%로 낮춰 쓰는 규칙도 같은 이유로 실적에 그대로 반영한다.Once the document and the ledger drift apart, nobody can later adjudicate which is right — so the document that actually went to customs is the reference. The same reasoning carries the return's reduced declared value straight into the ledger.
RULE 05
되돌릴 수 없는 지점을 명시한다Name the points that cannot be undone
WAS사람이 전 구간을 클릭했기 때문에 어디가 취소 불가인지 절차상 구분이 없었다.Because a person clicked through every screen, the procedure never distinguished which clicks were irreversible.
NOW재고를 움직이는 구간은 3PL 회신이 TO 번호와 명확히 매칭될 때만 자동 진행하고, 발송물 최종 생성은 사람이 요약 화면을 보고 누르는 유일한 체크포인트로 남겼다.The stage that moves stock proceeds only on an unambiguous match between the 3PL reply and the TO number; creating the shipment itself remains the single checkpoint a person confirms on the summary screen.
중복 실행 방지도 여기에 걸린다 — 상태 파일 잠금과 프로세스 잠금을 같이 두어, 한 회차가 다음 스캔 주기를 넘겨도 같은 TO가 두 번 처리되지 않는다.Duplicate-execution guards hang off the same rule: a state lock and a process lock together ensure the same order is never handled twice, even when one cycle runs past the next scan.
RULE 06
반송은 재배치와 다른 절차다A return is not a rebalance
WAS같은 알림 폴더로 들어오지만 목적지가 나라가 아닌 건은 절차가 없어 매번 수기로 처리했다.Alerts arriving in the same folder but destined for a headquarters organisation had no written procedure at all, and were handled by hand each time.
NOW목적지·HTS 코드·신고 금액·통관 문구·로케이터 유무·메일 제목·실적 기입·파일명·선언서·본사 서류 메일까지 10개 규칙을 독립 분기로 명문화했다.Ten rules — destination, HTS code, declared value, customs wording, whether locators apply, mail subject, ledger entry, file naming, the shipper's declaration, and the headquarters document mail — are codified as a separate branch.
분기를 켜기 전에 과거 수기 처리분을 이력에 먼저 채웠다. 매칭 범위를 넓히는 순간 몇 달 지난 건이 신규로 잡히기 때문이다 — 이제 매칭 확장 시의 표준 절차다.Before switching the branch on, previously hand-processed cases were seeded into the history — widening a trigger's scope otherwise resurfaces months-old cases as new. That check is now standard whenever matching widens.
RULE 07
스캔 주기는 업무시간이 아니라 하루 전체다Scan the whole day, not office hours
WAS업무시간(9~18시)에만 돌았다. 저녁에 도착한 트리거 3건이 하루 넘게 방치됐다.Scans ran only during office hours. Three triggers that arrived one evening sat untouched for over a day.
NOW트리거·회신 스캔 모두 24시간 30분 간격. 대기 건이 하나도 없으면 메일 폴더를 아예 열지 않게 막아 idle 비용을 없앴다.Both the trigger and reply scans run every thirty minutes around the clock, with a guard that skips opening the mail folder entirely when nothing is pending — so the idle cost is nil.
해외 법인이 만드는 알림은 우리 업무시간을 따르지 않는다. 아침 첫 실행이 메일 동기화보다 빨라 "없음"으로 끝나는 레이스도 실측으로 확인해, 짧은 주기로 자연스럽게 흡수되게 했다.Alerts raised by overseas entities don't keep Korean office hours. A race where the first morning scan outran the mail sync and returned "nothing" was also observed — a short interval absorbs it without special handling.

재고 이동 관리 리스트에 TO 번호가 배정되면 변경 알림 메일이 자동으로 날아온다. 본문에서 TO 번호와 출발·도착 법인, 파트를 읽어낸다. 한 TO에 파트가 여러 개면 파트마다 메일이 따로 오기 때문에 TO 번호 단위로 묶어 한 건으로 처리하고, 아직 TO 번호가 붙지 않은 등록 알림은 트리거 대상에서 제외한다.

Same folder, same alert format — but when the destination is a headquarters organisation (repair lab, refurb, purchasing) rather than a country code, it isn't a rebalance at all: it's a no-charge return to US headquarters. Everything about the paperwork diverges from here. The old pattern only recognised three-letter country codes, so this type had been silently ignored and handled by hand every time.

알림에는 파트 하나만 담겨 있어서, 그 TO 번호로 목록을 다시 조회해 실제로 나가야 할 파트와 수량 전부를 확정한다. 수입 통관 자동화가 이미 쓰고 있던 목록 조회 방식을 그대로 재사용하고 조회 기준만 TO 번호로 바꿨다.
The alert carries only one part, so the list is queried again by TO number to establish every part and quantity that actually has to ship. It reuses the same list-lookup routine the import-side automation already relied on, just keyed on TO number instead.

파트와 수량을 채운 요청 메일이 창고 담당자 앞으로 바로 나간다. 여기서 사람이 하던 일은 "무엇을 몇 개 꺼내야 하는지 정리해서 메일 쓰기"였고, 그게 통째로 없어진 구간이다.
A request email, already populated with parts and quantities, goes straight to the warehouse contact. The human work here used to be compiling what to pull and how many, then writing the mail — that whole step is gone.
WAITING— · —

여기서만 시스템 밖의 시간이 흐른다. 회신이 언제 올지 모르니 24시간 내내 30분마다 폴더를 훑고, 도착하면 그 즉시 이어서 진행한다. 대기 중인 건이 하나도 없으면 폴더를 아예 열지 않아 빈 회차의 비용이 없다.
This is the only stretch where time passes outside the system. Since the reply can land at any hour, the folder is swept every thirty minutes around the clock and the case picks up the instant it arrives — and with nothing pending the folder isn't opened at all, so an empty cycle costs nothing.
MAIL INSTEP 04
회신 파싱 + TO 매칭 판정
Parses the reply, judges the TO match
회신은 정해진 서식 없이 사람이 쓰는 대로 온다. 본문에서 TO 번호와 로케이터·수량을 뽑아내되, TO 번호가 확실히 특정될 때만 곧바로 다음 단계로 넘어가고 애매하면 자동 실행을 멈추고 사람 확인 알림만 보낸다 — 바로 다음이 실제 재고를 움직이는 구간이라 여기에 안전판을 뒀다.
Replies come in free-form, however the sender chose to write them. The TO number, locators, and quantities are extracted from the body — but the case only proceeds automatically when the TO number is unambiguous; anything murky halts and raises a human-review alert instead, because the very next stage moves real inventory.
ORACLESTEP 05–09
재고를 실제로 움직이는 5개 트랜잭션

회신이 파싱된 순간 사람 명령 없이 이어서 실행된다. 중간에 끊겨도 이미 통과한 단계를 다시 누르지 않도록 진행 상태를 단계별로 남기며 간다 — 재고 이동은 되돌릴 수 없어서 재시도와 중복 실행 방지를 같이 걸어야 했다.
Runs straight through with no manual command the moment the reply is parsed. Progress is recorded stage by stage so an interruption never re-clicks a step that already went through — inventory movement can't be undone, so retries and duplicate-execution guards had to be built together.

DOCUMENTSTEP 11–12
통관 Commercial Invoice 발급 + PDF 보정
Issues the customs invoice, then patches the PDF
수입 통관 자동화가 쓰던 인보이스 출력 경로를 그대로 재사용하되 출발지를 한국으로 돌려 발급한다. 오라클이 뽑아준 PDF에는 목적지 국가별 수하인 정보와 HTS 코드 칸이 비어 있어서, 서식을 새로 만들지 않고 원본 PDF의 빈 여백에만 값을 직접 얹는다 — 인쇄 레이아웃이 그대로 유지돼야 통관 서류로 쓸 수 있기 때문이다. 파트가 여러 개인 건은 행마다 HTS 코드를 각각 채운다.
Reuses the very same invoice-printing path as the import automation, just pointed outbound from Korea. On multi-part shipments, every line gets its own HTS code.
RMA ONLYSTEP 11–12
반송 건의 서류 규칙 — 신고가·선언서·본사 통보
Return-only rules — declared value, declaration, HQ notice
반송은 파는 물건이 아니라 고장난 부품이 제조사로 돌아가는 것이라, 인보이스 금액을 그대로 쓰면 안 된다. 단가·품목금액·소계·총계를 전부 원본의 10%로 다시 쓰고, HTS 코드는 파트와 무관하게 재반입 조항으로 고정하며, 그 금액의 근거가 되는 통관 문구를 품목표 아래 빈 띠에 넣는다. 여기에 반송에 반드시 따라붙는 선언서(Foreign Shipper Declaration)를 양식에서 자동 생성해 인보이스와 함께 본사 담당자 앞 메일에 붙인다.
A return isn't merchandise — it's a faulty part going back to its manufacturer, so the invoice value cannot stand. Unit prices, line amounts, subtotal, and total are all rewritten to a tenth of the original, the HTS code is pinned to the re-entry provision regardless of the part, and the customs sentence justifying that value is placed in the blank band under the item table. The shipper's declaration that always accompanies a return is generated from its template and attached, alongside the invoice, to a mail addressed to headquarters.
금액을 다시 그리면 PDF의 텍스트 묶음이 깨져 품목 파싱이 무너지기 때문에, 실적에 쓸 값은 금액을 손대기 전 원본에서 읽고 코드 안에서 10%를 곱한다. 같은 파트가 시리얼별로 여러 줄에 걸쳐 있어서 선언서와 실적 수량은 파트당 합산해야 맞는다.
Redrawing the amounts breaks the PDF's text grouping and with it the item parser, so the values destined for the ledger are read from the untouched original and scaled in code instead. The same part also spans several rows by serial number, so the declaration and the ledger quantity only come out right when aggregated per part.

The moment the invoice is final, the case moves straight into the booking screens. Box dimensions come from the original 3PL reply, item values from the invoice just issued — the stretch where a person used to copy back and forth between two documents is simply gone.

발송물을 만드는 순간은 되돌릴 수 없다. 그래서 요약 화면까지만 자동으로 채워두고, 확정 클릭은 사람이 내용을 보고 누르는 지점으로 남겼다. 실패해도 탭을 닫지 않는다 — 5~8분치 입력을 날리고 처음부터 다시 태우는 낭비를 없앤 규칙이다.
Creating the shipment cannot be reversed, so the flow fills everything up to the summary and leaves the confirming click to a person who has read it. On failure the tab is left open — the rule that ended the waste of discarding five to eight minutes of entry and starting over.

Label out, tracking written back
생성 성공 화면에서 트래킹 번호를 읽고 라벨을 내려받은 뒤, 서류를 보냈던 3PL 답장 스레드에 라벨을 붙여 보내고, 같은 번호를 재고 이동 목록과 수출신고실적 B/L 칸에 되돌려 적는다. 트래킹 번호는 오직 성공 화면의 배송 조회 앵커에서만 읽는다 — 열려 있던 다른 탭의 12자리 숫자를 트래킹으로 착각해 잘못된 번호를 기입한 사고 이후 못 박은 규칙이다.
The tracking number is read off the creation-success screen and the label downloaded, then the label goes out on the same 3PL thread that carried the documents, and the number is written back into both the stock-movement list and the waybill column of the export ledger. That number is read only from the shipment-ID anchor on the success screen — a rule nailed down after a 12-digit value from an unrelated open tab was mistaken for it.
처리 결과는 상태 파일에 남아 같은 TO가 다시 트리거돼도 두 번 처리되지 않는다. 여기까지 오면 남는 일은 창고가 상자를 실어 보내는 것뿐이다.
The outcome is recorded in the state file, so the same order can never be processed twice even if it triggers again. Past this point the only thing left is the warehouse handing the boxes over.

13개 컬럼이 전부 자동으로 채워진다. 마지막 B/L 칸은 오래 비어 있던 자리였다 — 택배사가 발송물을 만들어야 비로소 생기는 번호라 시스템 안에서 미리 만들어낼 수 없었기 때문이다. 발송 어레인지를 파이프라인 안으로 끌어들이면서 그 칸도 닫혔고, 사람이 하는 일은 요약 화면을 한 번 확인하는 것으로 줄었다. All thirteen columns now fill themselves. The waybill column at the end sat empty for a long time — the number doesn't exist until the courier creates the shipment, so nothing inside the system could conjure it. Pulling the booking itself into the pipeline closed that column too, and the human share came down to reading one summary screen.
