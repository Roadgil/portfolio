업무를 맡는AGENTS THAT
AI 에이전트OWN A JOB

질문에 답하는 챗봇이 아니라, 한 업무를 처음부터 끝까지 맡는 에이전트를 직접 설계하고 운영한다. 업무를 먼저 Claude와 대화로 처리해 보면서 규칙을 확정하고, 확정된 규칙과 검증된 도구만 에이전트 정의 파일로 옮긴다. 대표 사례는 병원 출고 요청 메일을 Salesforce 파트오더로 만들고 Oracle 전송·릴리즈·창고 안내 메일까지 이어가는 파트오더 에이전트, 그리고 독일 공급사 구매를 16단계 SOP대로 진행하는 Zimmer 구매 에이전트. 되돌리기 어려운 단계(승인 요청, Submit, 메일 발송)는 사람이 결정한다. Not a chatbot that answers questions, but agents designed and run to own one job end to end. The work is first done with Claude in conversation until the rules settle, and only those settled rules and the tools that proved themselves move into an agent definition file. The main examples are a parts-order agent that turns hospital shipment-request emails into Salesforce parts orders and carries them through Oracle interface, release and the warehouse notice, and a Zimmer procurement agent that runs purchasing from a German supplier along a 16-step SOP. Steps that are hard to undo (approval requests, Submit, sending email) stay a human decision.

Agent Definition

정의 파일에 들어간What the definition
규칙들file holds

ROLE · TOOLS
역할과 허용 도구를 먼저 못 박는다. 메일 검색 · Salesforce 조회 · 로컬 스크립트 실행 등 13개만 쓸 수 있다.
Role and allowed tools come first: thirteen, covering mail search, Salesforce queries and local scripts.
메인 대화에서 "파트오더 만들어줘", "승인 났어 릴리즈 해줘"라고 하면 이 에이전트로 넘어간다.
Phrases like "create the parts orders" or "approved, release them" route the work to this agent.
HARD RULES
승인 요청은 직접 지시가 있을 때만. 메일은 기본 초안. 상태 파일과 업무 엑셀은 백업 없이 고치지 않는다.
Approval only on direct instruction. Email defaults to draft. State files and working spreadsheets are never edited without a backup.
누른 버튼은 몇 시 몇 분에 눌렀는지까지 보고해, 사람이 한 번 더 누르는 중복을 막는다.
Every click is reported with its time, so nobody presses it a second time.
INCIDENT → RULE
오후 요청 2건이 빠진 날 이후, 하루 끝에 그날 요청 메일 전체와 생성된 주문을 대조하는 단계를 추가했다.
After a day when two afternoon requests were missed, an end-of-day check was added that matches every request email against the orders created.
체인 병원 지점 간 입금 오매칭이 나온 뒤에는 지점명까지 일치해야 확인으로 인정하도록 바꿨다.
After a deposit matched the wrong branch of a clinic chain, a match now requires the branch name too.
PORTABLE
에이전트 본체와 설치 가이드를 공유 폴더에 두어, 다른 PC의 Claude Code에도 같은 에이전트를 심을 수 있게 했다.
The agent definition and an install guide live in a shared folder, so the same agent can be set up in Claude Code on another PC.
가이드에는 준비물, 하루 흐름(사용자 말 → 에이전트 동작 → 도구), 알려진 함정을 표로 정리했다.
The guide tabulates prerequisites, the daily flow (what the user says, what the agent does, which tool) and known traps.

SOP · 16 STEPS
SOP를 읽고 단계별로 진행
Reads the SOP, works step by step
대표 승인 요청부터 Oracle 구매요청, PO 전환 요청, 공급사 발주서, PI/OC 대조, 재무 지급요청, 제작 요청, 수입 운송 예약까지 16단계를 에이전트가 이어간다.
From the approval request through the Oracle requisition, PO conversion, supplier order, PI/OC check, finance payment request, production request and import booking, the agent carries all sixteen steps.
Oracle 구매요청은 Playwright로 장바구니까지만 채우고 Submit은 사람Playwright fills the Oracle requisition up to the cart; a person submits
지급요청 날짜는 재무 지급 일정에 맞춰 제안Payment requests are dated to the finance payment calendar
EXCEPTION → SOP
예외를 SOP에 다시 쓴다
Writes exceptions back into the SOP
품목코드가 없는 부품은 기존 SOP에 절차가 없었다. 실제 건으로 입력 경로와 계정을 확정한 뒤, 같은 방식으로 자동 PO 생성까지 확인하고 SOP 문서에 예외 장으로 추가했다.
Parts with no item code had no procedure in the SOP. The entry path and account were settled on a live order, automatic PO creation was confirmed, and the result was added to the SOP as an exceptions chapter.
문서 하단 고정 문구를 계좌 변경으로 오판한 뒤 IBAN 비교로 판단 기준 변경After misreading a boilerplate footer as a bank change, the check moved to comparing IBANs
FULL CASE
공급사 구매 P2P 상세
Supplier P2P in full
단계별 화면, 발주서 생성, 수입 운송·통관 기록 연계는 공급사 구매 페이지에 정리했다.
Screens per step, PO generation and the import freight and customs records are on the supplier procurement page.
