Warranty & Contract PM · Google Apps Script · Personalized Alerts

Monthly VisitMONTHLY VISIT
정기점검(PM) 자동알림PM AUTO-ALERT WEBAPP

Google Apps Script + Google Sheets로 만든 장비 정기점검(PM) 관리 웹앱. 장비구입(워런티 1년, 시작일+5/10개월)과 컨트랙(계약기간 무관, 시작일+3/7/10개월) 두 가지 규칙으로 방문 일정을 자동 계산한다. Brick(영업권역)별 담당 FSE에게는 URL 파라미터로 개인화한 링크를 발급해, 본인 담당 건만 팝업으로 Yes/No 응답과 비고를 받고 매주 월요일 자동 메일로 리마인드한다. 설치기반(ISB) 리포트를 xlsx 원본 그대로 업로드하면 브라우저에서 Billing Type만 걸러 일괄 등록된다. A Google Apps Script + Google Sheets webapp that manages equipment PM visits under two rules — warranty (1-year, start date +5/10 months) and contract (regardless of length, start date +3/7/10 months). Each FSE gets a Brick-specific link via URL parameter, so only their own units pop up for a Yes/No response with notes, plus a Monday auto-email reminder. Uploading the raw installed-base (ISB) report as-is filters by Billing Type in the browser and bulk-registers the rest.

1,274건 중 619건만 규칙 대상
Only 619 of 1,274 rows apply
설치기반(ISB) 리포트 1,274건 전부를 그대로 넣으면 안 된다. Billing Type이 Warranty(283) 또는 Contract(336)인 619건만 PM 규칙 대상이고, Billable·Sales Support 655건은 자동 제외해야 한다 - 업로드 시 브라우저에서 바로 필터링하도록 처리.
Not all 1,274 rows in the installed-base (ISB) report belong in the PM cycle. Only rows with Billing Type Warranty (283) or Contract (336) — 619 total — are in scope; the other 655 (Billable, Sales Support) get auto-excluded right in the browser at upload time.
🔗
로그인 계정 ≠ 회사 이메일
Login account ≠ company email
회사 이메일은 M365(Outlook)인데, 웹앱 로그인은 구글 계정이라 서로 다른 계정이다. Session.getActiveUser()로 담당자를 구분하려던 첫 시도는 무산됐고, 대신 브릭별 URL 쿼리파라미터(?brick=N)로 FSE마다 다른 링크를 발급해 개인화 알림을 우회 구현했다.
Company email runs on M365 (Outlook), but webapp login uses a Google account — two separate identities. The first attempt to distinguish FSEs via Session.getActiveUser() didn't hold up; personalization was instead solved with a per-Brick URL query parameter (?brick=N), giving each FSE their own link.
♻️
중복 업로드 사고 → dedupe
Duplicate upload → dedupe guard
같은 ISB 파일을 실수로 두 번 업로드해 장비가 정확히 2배(1,238건)로 늘어난 걸 발견한 뒤, ProductID 기준 중복 제거 로직을 추가했다. 이후로는 전체 리스트를 다시 올려도 이미 등록된 ProductID는 자동으로 건너뛴다.
After noticing equipment count had exactly doubled (1,238) from an accidental double-upload of the same ISB file, a ProductID-based dedupe guard was added — re-uploading the full list now silently skips anything already registered.

실행 로그로 검증한 것만 올림
Only what the execution log confirmed
매주 월요일 자동 메일은 Apps Script 실행 로그로 Brick 1~7 담당자 전원에게 발송 성공한 것을 직접 확인했다. 한 명이라도 발송 중 오류가 나면 나머지 전원이 조용히 발송 중단되는 구조였던 걸 발견해, 발송을 하나씩 try/catch로 감싸 한 명의 실패가 나머지를 막지 않게 고쳤다.
The Monday auto-email was verified by execution log to send successfully to all seven Brick recipients. Along the way, one recipient's send failure was found to silently abort the rest of the loop — fixed by wrapping each send in its own try/catch so one failure no longer blocks everyone else.
